# Repository Guidelines

## Project Overview

Personal Novel Translator (PNT) is a multi-account novel translation app. It supports EN→TH by default plus ZH→EN and ZH→TH, public sign-up, guest read-only access to published content, chapter paste/scraping, OpenAI-compatible translation providers, a synchronized reader, glossary/summary consistency, and TXT/EPUB export. Every account owns an isolated workspace; an optional operator (`admin`) role gates account administration. The web app lives at the repository root; a single `package.json` and `bun.lock` drive the app, its scripts, and its tooling.

## Architecture & Data Flow

- **Web runtime:** TanStack Start with React 19, TanStack Router/Query, Vite, and Nitro for Vercel. File-based routes live in `src/routes/`; `src/router.tsx` supplies the Query client and SSR query integration.
- **Request/auth flow:** `src/routes/__root.tsx` loads the nullable session into router context. `_public` routes serve guests and signed-in readers (`/` is the shared catalog for a guest and the reading home for an account, `/catalog` is the shared catalog at its own URL with `/browse` redirecting to it, and `/library` is an account's own shelf); `_protected` redirects unauthenticated users to `/login`, and `/_protected/admin` redirects non-operators home. API routes handle auth, covers, avatars, exports, Inngest, sitemap, and robots responses. Sign-up, verification, password reset, email change, session management, and deletion run through Better Auth endpoints; the operator screens call the admin plugin through `src/lib/admin/functions.ts`.
- **Operator controls:** `/admin` is three tabs: accounts (`_protected/admin.index.tsx`), the member-report queue (`_protected/admin.reports.tsx`), and the audit trail (`_protected/admin.activity.tsx`), behind `ensureAdminSession` everywhere and never targeting the acting operator. A suspension is the plugin's own `banned`/`banReason`/`banExpires`, so its status is read through `describeBan` (`src/lib/admin/ban-status.ts`) rather than the stored flag, which the plugin only clears when that account next signs in. Impersonation is read-only by construction: `requireSession` refuses a session whose `impersonatedBy` is set, and every mutation authenticates through it, while reads use `getSession` or `ensureSessionForRead`. Every operator action also appends to `admin_audit_log` through `src/lib/admin/audit.server.ts`; that write happens after the plugin mutation and is never allowed to report the mutation as failed.
- **Reporting flow:** A signed-in member reports a published novel they do not own, a chapter comment, or a review; the queue groups every open report on one target into a case (`caseKey` is the target id — novel, comment, or review — or a report id once that target is deleted) and one decision — `upheld`/`dismissed` plus a note — moves every open report in it in a single statement. A decision records only: it never suspends, unpublishes, or deletes, and a second operator racing the same case is told it was already decided. Operators get a separate, audited **Remove content** action for comment and review cases (`comment.removed` / `review.removed`), which needs its own reason and leaves the case open. Reports snapshot the novel title and the reported words and clear their target column on delete, so a case outlives the content it names; partial unique indexes allow one open report per account per target, and filing is metered per account.
- **Follows and notifications:** `src/lib/notifications/` owns follows and the in-app bell. A signed-in reader follows a novel they do not own; `novel_follows` is keyed by that pair. Five writers produce rows in `notifications`: a live chapter fans out to its followers (excluding the author), a top-level comment notifies the novel's owner, a reply notifies its parent's author, a new review notifies the novel's owner, and a decided report notifies each reporter. Fan-out is idempotent through `unique(user_id, dedupe_key)`, a `chapter_published` row exists only while its chapter is live (publishing/unpublishing reconciles it), and every write is best-effort — `runNotificationWrite` logs and moves on, because a missing badge must never fail the publish, comment, or decision that caused it. A single-chapter publish fans out inline after commit; a bulk release and a scheduled chapter are picked up by a one-minute Inngest sweep. Ably only accelerates delivery: `/api/realtime/token` mints a subscribe-only token for the session's own channel, the client refetches on each message, and the query polls every 30 seconds so an absent `ABLY_API_KEY` costs no correctness.
- **Discussion and reviews:** `src/lib/comments/` and `src/lib/reviews/` own chapter discussions and novel reviews. Comments are one level deep, follow their chapter's publication exactly (a draft collects none, for its owner included), and render an operator-removed or author-deleted comment as a tombstone while replies exist so other readers' words are never collateral. A review is one live rating per account per novel (partial unique index), text optional, and the summary counts only live reviews, so a removal moves the average immediately. Guests read both; writing goes through `ensureSession` and per-account meters. Account deletion tombstones the account's comments (keeping threads intact) and cascades its reviews out of every average.
- **Server boundary:** Route-facing operations use TanStack `createServerFn`, validate input with colocated Zod schemas, authenticate with `getSession`/`ensureSession` (or `ensureAdminSession` for operator work), query Drizzle, and wrap failures with `withSafeHandler`. Database, environment, provider keys, and Node-only code stay in server-only modules. A `createServerFn` whose module no client graph imports has no RPC identity and fails at runtime, so server-to-server helpers are `createServerOnlyFn`.
- **Persistence:** `src/lib/db/schema/` defines the PostgreSQL tables for users/auth, novels/chapters, glossary terms, provider settings, jobs, chunks, outbox events, imports, rate limits, evaluation reports, and member reports. `src/lib/db/index.ts` creates the Drizzle client with a single pooled connection per process (`prepare: false`, recycled on idle and lifetime bounds) against the pooled `DATABASE_URL`, so serverless fan-out is multiplexed by the provider's pooler; migrations and drizzle-kit use the direct `DATABASE_URL_UNPOOLED` instead, because DDL and prepared statements need a real session. The optional `DATABASE_POOL_MAX` (default `1`) exists only for the integration suites that assert row-lock contention between two concurrent transactions; a single connection would serialize them client-side and Postgres would never report the waiter.
- **Translation flow:** The browser only enqueues/cancels/retries jobs and polls read-only status; it never runs translation. An enqueue transaction locks the chapter, chunks raw text, invalidates prior active work, writes job/chunk rows, advances chapter generation, and records a `translation_outbox` event. Inngest runs `init`, one memoized `chunk-N` step per chunk (relationship analysis plus translation), and `finalize`, with retries, cancellation, per-novel concurrency, and `runKey` idempotency; `init` memoizes the run-stable context (approved glossary terms, previous-chapter tails) for every chunk step. `worker.ts`, `job-store.ts`, `job-state.ts`, `run-context.ts`, and `outbox.ts` enforce generation/source-revision/active-job ownership and atomic finalization.
- **Import/scrape flow:** `src/lib/scrape/index.ts` exposes client-safe metadata and pure parsers. Server fetches go through bounded HTTPS/manual-redirect checks and `src/lib/scrape/network-policy.server.ts` SSRF/DNS protections. Bulk imports are resumable Inngest jobs with one chapter step at a time.
- **Object storage:** `src/lib/storage/` is the only place that talks to a bucket. Covers are validated and re-encoded into per-width WebP variants in the public bucket under `covers/<novelId>/<unguessable segment>/`; EPUB upload archives and cached exports live in the private bucket behind signed URLs or the app's own routes. Keys and the export cache fingerprint are derived in the pure `keys.ts`; `r2.server.ts` speaks the R2 S3 API through `s3mini` with its `fetch` pinned to the global (which keeps one code path across Bun and Node), `local.server.ts` is the filesystem adapter, and `index.server.ts` selects one. Caching is a rule on the public cover domain, never a per-object header. With no `R2_*` configuration the app falls back to `.tura/storage/`, so uploads, cleanup, and exports stay testable without a bucket. The six `R2_*` variables are all-or-nothing; Vercel requires all six. Nothing removes anything without a rule: the daily storage sweep prunes what a deleted row owned and reaps what a surviving row stopped naming (a superseded cover segment, a cached export revision the content moved past, a staged archive no upload row names), and it may only remove a set whose newest object is older than `SUPERSEDED_GRACE_MS` — a listing reports when each object was written (`listObjects`), because every writer here puts its objects down before the row that names them.
- **Visibility/export:** Guest reads apply novel and chapter `publishedAt` live filters and guest rate limits; mutations always require a session and ownership. Authenticated exports stream chapters in numeric order through a PostgreSQL cursor as TXT/EPUB rather than buffering a whole novel.
- **Durable invariants:** `architect.md` is authoritative for job state, stale-worker rejection, source revision/generation rules, outbox delivery, per-novel ordering, glossary propagation, export streaming, object-storage key/caching and residue-sweeping rules, and scrape client/server boundaries.

## Code Conventions & Common Patterns

- **TypeScript:** Strict compiler settings, no unused locals/parameters, no explicit `any`, no unchecked side-effect imports, and no fallthrough. Prefer named exports, descriptive camelCase symbols, and colocated leaf types such as `translation/types/*.ts`, `reader/types.ts`, and `*.schemas.ts` for Zod-inferred inputs. Use `@/` (or `#/`) aliases instead of long relative imports.
- **Folder organization:** A domain folder that outgrows a flat listing splits into role subfolders (`chapters/table/`, `chapters/import/`, `novels/detail/`, `lib/content/chapter/`, `translation/workflow/`), not one folder per file. Keep leaf filenames unchanged, colocate `*.test.ts(x)` with the module, leave domain-wide `*.integration.test.ts` at the domain root, and keep modules shared across subfolders at the domain root. There are no barrel `index.ts` re-exports — import the module directly through `@/`, using relative paths only for same-folder siblings.
- **Server functions:** Follow `createServerFn({ method })` + `.validator(schema)` + `.handler(...)`. Use `ensureSession()` for mutations, verify resource ownership through the novel/user join, apply guest publication filters and `checkRateLimit` to public reads, and return safe errors through `withSafeHandler`/`SafeServerError`. Keep server-only work behind a `*.server.ts` service and export only server functions from the module client code imports: a plain export that reaches a `.server` module survives into the client bundle and fails the build's import protection.
- **Errors and untrusted data:** Catch variables are `unknown`; narrow with `instanceof Error`. Validate request/form/JSON input with Zod. Unknown server failures are logged and exposed as a generic safe message. Do not leak provider keys or internal database details.
- **Database/state:** Drizzle properties are camelCase over snake_case columns. Use `nanoid()` IDs, transactions, and `for('update')` locks for job ownership/state changes. Keep source revisions, translation generations, active job IDs, and outbox intent consistent; do not implement worker validity rules in route handlers.
- **Async jobs:** Keep LLM work in Inngest workers. Use memoized steps and explicit cancellation/idempotency; sequential chunk loops are intentional because each chunk depends on prior context. Client job hooks are refresh-safe polling/enqueue controls, not workers. Use `Promise.all` only for independent reads.
- **Client state:** Use TanStack Query loaders/query options and invalidate affected keys after mutations. Reader `fontSize`, `typeface`, and `viewMode` persist under `pnt-reader-settings`; app theme belongs to `next-themes`, not reader-local state. Avoid single-key shortcuts while focus is in form fields.
- **UI/design:** Use shadcn components on Base UI primitives and Tailwind semantic design tokens from `src/styles/globals.css`. Prefer semantic `background`, `foreground`, `muted-foreground`, `border`, `surface`, and `primary` utilities so dark mode works. Keep the Sofia Sans + Noto Sans Thai stack (Sarabun is the reader option), warm surfaces, restrained borders, and shallow depth; avoid arbitrary gray/hex colors, pure white/black, heavy card shadows, saturated accents, and weight 700. Consult `DESIGN.md` before changing UI.
- **Security boundaries:** Keep environment access in `src/lib/env.ts`; provider API keys are encrypted at rest. Authorization is ownership plus the `admin` role; the role is granted only out of band (`bun run seed:user` or an existing operator) and never from client input. Operator functions refuse to target the acting operator's own account. Scraping must preserve host allowlists, HTTPS, manual redirect rejection, body/time limits, and private-IP blocking. Covers require content validation, not only a declared MIME type, and are stored only as re-encoded variants, so upload bytes never reach the bucket or the CDN as-is. Keep private-bucket objects out of public responses; serve them through signed URLs or the app's own authenticated routes.
- **Object keys:** Build keys and prefixes with `src/lib/storage/keys.ts` helpers instead of string concatenation — no module outside that one spells a key, which `keys.test.ts` holds the tree to. The helpers return branded `ObjectKey`/`KeySetPrefix` values, and the port and the adapters beneath it take only those, so a plain string is refused at compile time and a value that arrived as data (a row, a listing, a request) is read back with `parseObjectKey`/`isObjectKeyPrefix` before it can be used. A prefix names a key set (`covers/<novelId>/<segment>`, `covers/<novelId>`), which `keySetScope` resolves once — in `port.ts`, before any adapter sees it — into the set's name and the boundary a raw-prefix store works on, so a set never reaches a sibling that merely shares its characters, callers never write the separator themselves, and an adapter cannot scope a set differently from another. The same module reads a key back to its owner (`ownerOfObjectKey`), which is the only ownership rule: the reconciliation that prunes a deleted novel's bytes and the read-only `bun run storage:audit` report both work from it, and a key it cannot read is unowned rather than deletable. The port itself refuses a key or prefix the vocabulary does not derive (`port.ts`, which builds the selected adapter into the `ObjectStorage` the app uses — `ObjectStorageBackend` is what an adapter implements), so a hand-built key cannot reach a bucket even if a caller tries. Cover keys carry an unguessable segment so a replacement is a new URL rather than a purge, and the export cache key is a content fingerprint — cover or publication edits deliberately do not invalidate a cached export.
- **Generated/configured files:** Never hand-edit `src/routeTree.gen.ts`, `drizzle/*.sql`, `drizzle/meta/*.json`, or build output. Update route source/config and regenerate. Preserve current dependency pins/ranges and security/tooling overrides unless intentionally changing the dependency policy.

## Runtime/Tooling Preferences

- Required package manager/runtime: **Bun 1.4.2**, with `bun.lock`; the package is ESM (`"type": "module"`). Do not substitute npm/pnpm commands or floating CLI versions.
- **Nitro:** `nitro` is an exact alias for the nightly build (`npm:nitro-nightly@…`); keep it pinned. The former workspace-only `h3-rules` shim was removed when the repo flattened back to a single package — re-add it only if a Nitro upgrade reintroduces app-root resolution problems.
- Application stack: React 19, TanStack Start/Router/Query, Vite, Tailwind v4 CSS-first tokens, shadcn Base UI, Drizzle/PostgreSQL, Better Auth, Inngest, and Nitro/Vercel.
- Formatting/linting: Oxfmt and Oxlint are canonical; there is no ESLint/Prettier/Biome workflow. `react-doctor` is a separate diagnostics command.
- **Environment:** copy `.env.example` to `.env.local`; access server env only through `src/lib/env.ts`. `TEST_DATABASE_URL` is test-only — read directly by `*.integration.test.ts`, not by `env.ts` — and must name a disposable database. Local Inngest is keyless with `INNGEST_DEV=1`; production requires Inngest Cloud event/signing keys. Transactional email (`RESEND_API_KEY` + `EMAIL_FROM`), Turnstile, and each OAuth provider are optional but paired: a lone half is a boot-time configuration error, and an absent pair disables that method instead of showing a button that cannot work. Never commit `.env*`, provider credentials, or linked Vercel metadata.
- Database: use a PostgreSQL `DATABASE_URL`; run migrations explicitly. Integration/E2E databases must be disposable and isolated. Object storage is optional locally (the `.tura/storage/` filesystem adapter) and mandatory on Vercel; `bun run storage:migrate` must run before `bun run db:migrate` on any database still holding legacy cover bytes, because migration 0038 drops `novels.cover` and `epub_upload_chunks`. Migration 0039 adds the Better Auth admin-plugin and terms-acceptance columns to `user`/`session`; they are nullable and additive, and every account created before it simply has no recorded role — the seeded operator is created (or repaired) by `bun run seed:user`.
- **Deployment:** Nitro targets Vercel. Set the project Root Directory to the repository root; `vercel.json` uses a frozen install and the postbuild patch for a 300-second server function budget. The app's Inngest endpoint is `/api/inngest`.

## Testing & QA

- **Unit tests:** Vitest runs colocated `src/**/*.test.ts`/`.test.tsx` files. `bun run test` excludes `**/*.integration.test.ts` and `e2e/**`. Tests should defend observable behavior, boundaries, state transitions, error handling, and compatibility—not implementation details. No coverage threshold/config is defined; preserve meaningful contract coverage. `vite.config.ts` forces `NODE_ENV=test` through Vitest's `test.env`, because an inherited `NODE_ENV=production` makes React resolve its production build and fails every render test with `React.act is not a function`.
- **Integration tests:** `bun run test:integration` runs the explicit translation workflow/outbox/chunk migration, export streaming, content maintenance, member reporting, and storage-backed EPUB/export suites. `TEST_DATABASE_URL` comes from `.env.example`/`.env.local` — Bun loads it, so no inline export is needed — and must point at an isolated, disposable database; never let integration tests fall back to `DATABASE_URL`. The E2E supervisor names its own database the same way (`E2E_DATABASE_URL`, `_e2e` required), so one guard covers every entry point that names one.
  `bun run db:migrate:test` creates that database when missing and applies migrations against it, through the same disposable-name rule every entry point that names a database applies (`src/lib/db/database-url.ts`); it is the run's template, not the database the suites touch. Suites skip themselves when `TEST_DATABASE_URL` is unset. Each suite runs in its own Vitest worker against its own clone of that template (`suiteDatabaseName`), so the suites run concurrently — bounded by `--maxWorkers=4`, because each one holds its own client open and PostgreSQL's default ceiling is a hundred — without sharing rows, and a whole-table sweep is a suite's own business rather than an allowance. The clones are dropped and re-cloned before every run and left in place afterwards, so a failed suite can still be inspected. What a suite still declares is what reaches past its own database or worker: the environment `src/lib/env.ts` reads at first import, a widened pool for a suite that contends on a row lock, and a sibling database for a suite that migrates one. Those are declared once in `src/test/integration-declaration.ts`, which is also the run's file list: `scripts/test-integration.ts` runs exactly `INTEGRATION_SUITES`, so a suite that is declared is run and a suite that is run is declared. Naming a suite on the command line (`bun run test:integration -- lib/export/stream.integration.test.ts`, or any unique tail of that path) narrows the run to it, matched against the declaration, so a name the declaration does not have is refused rather than handed to the runner as a path that matches nothing. The door the suites go through is `src/test/integration.ts`: `openIntegrationDatabase(import.meta.url)` points the suite at its own clone, applies the environment and the allowances, and refuses an undeclared suite, a second open, and a database that does not read as disposable, and `closeIntegrationDatabase` in `afterAll` hands the connection back, so the door owns its lifetime. Object storage is still shared across the concurrently running suites, which is safe because every key carries its own UUID or content fingerprint, and the run removes what it writes: `scripts/test-integration.ts` reads both buckets immediately before Vitest starts and deletes the sets the run created once it has exited (`scripts/bucket-footprint.ts`), one window around the whole run rather than one per suite, because the suites run concurrently and a suite's own sweep could delete a set a sibling was still asserting on. The database guard is not enough on its own here: a suite's rows are dropped with its clone while the objects it staged stay in the bucket, and the sweeps that empty the bucket work from rows, so a set whose row is gone is reaped by nobody. `src/test/integration.test.ts` holds those declarations against the tree and the suite sources.
- **E2E:** `bun run test:e2e` uses `scripts/e2e/run.ts` to claim a database of its own through the same guard the integration run uses — `requireDisposableDatabaseUrl` in `src/lib/db/database-url.ts`, with a `_e2e` ending required on top of the rule, so the application's database and the integration template are each refused — then drops and re-creates it, applies migrations, seeds an admin/provider through `scripts/e2e/prepare.ts` (guarded identically), starts the app, Inngest dev server, and deterministic OpenAI-compatible stub, then runs Playwright. It requires an installed Chrome or Edge; no browser download is attempted. The workflow covers login, novel/chapter creation, real queued translation, publication, logout, and guest reading. It also removes what it wrote: `scripts/e2e/run.ts` takes the same bucket footprint under the environment it composed for its children, and sweeps it in its `finally`, after every process it started has stopped and before the database it seeded is dropped.
- **CI gate:** `.github/workflows/ci.yml` runs frozen Bun install, migrations, `format:check`, lint, typecheck, unit tests, PostgreSQL integration tests, E2E, build/postbuild output smoke, and the moderate-level dependency audit. Run the relevant command locally before claiming a change is complete; use `bun run doctor` for React-specific diagnostics.
